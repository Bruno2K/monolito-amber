# M4.1 migration, seed, and rollback plan

**Status:** Plan only. **No migration is applied in M4.1.**  
**Issue:** [#54](https://github.com/Bruno2K/monolito-amber/issues/54).  
**Base:** current `main` @ `a3eaadcd61c8f8153f61c6a51f920e37b8f362a0` (PF-1.5 + M3.3–M3.7 already applied).

Goal: upgrade this tip in later M4 WIs **without destroying or rewriting operational history**.

## Current applied Planning DDL (KEEP)

| Migration | What it did |
| --- | --- |
| `20260922220000_pf_1_5_planning_tasks_milestones` | Created `planning` schema, `tasks`, `task_dependencies`, `milestones`, CHECKs, tenant triggers, grants |
| `20261001200000_m3_7_cross_domain_traceability` | Additive Task/Milestone delivery FKs + schedule fields; **CREATE OR REPLACE** tenant functions (expand, not drop history) |

Operational tables that Planning must not truncate, drop, or rewrite: `planning.tasks`, `planning.task_dependencies`, `planning.milestones`, `operations.*`, `coordination.issues`, `project.project_memberships`, `document.*`, `audit.audit_events`.

Historical string `planning.tasks.responsible_discipline_id` stays. Do not `DROP` / `RENAME` / wipe it (same rule as M3.1).

## Forward path for later M4 WIs

M4.2–M4.7 are expected to be **API/UI/read-model** work on the existing columns. A new Prisma migration is **not** required to freeze the contract.

If a later WI proves a need, it may add **only**:

1. **Indexes** on existing Planning columns used by the unified query (e.g. `(project_id, status)`, `(project_id, due_date)`). Additive `CREATE INDEX IF NOT EXISTS`.
2. **Seed / fixture rows** (no DDL) for Local RC Planning demos.
3. A dependency-unlink path that **deletes an edge row** (not Task history) if M4.4 authorizes it — still not a destructive table rewrite.

Forbidden in any M4 migration SQL:

- `DROP TABLE` / `TRUNCATE` of Planning or Operations history
- Changing Task/Milestone CHECK enums to include `OVERDUE`, `AT_RISK`, `MISSED`, `PLANEJADA`, `EM_RISCO`
- Persisting Kanban Portuguese labels
- Backfilling stored AT_RISK/MISSED
- Auto-writing `status` from dates
- `gate.override`
- Rewriting audit rows

## Seed

M3 seed (`AMBER_SEED_M3=1`, `prisma/m3-seed.ts`) has orgs, memberships, Phases, Deliverables, WorkPackages, and negatives. It does **not** create Planning Tasks/Milestones.

**M4.8** (not this WI) should additively upsert synthetic Planning fixtures on the existing demo projects:

| Class | Intent |
| --- | --- |
| Tasks in each stored status | TODO, IN_PROGRESS, BLOCKED (with reason), DONE, CANCELLED |
| Late TODO / IN_PROGRESS | Drive Kanban `EM RISCO` and Milestone `AT_RISK` |
| FS pair | Predecessor DONE + successor TODO; plus a blocked-start pair |
| Milestone PLANNED / ACHIEVED / CANCELLED | Plus one past `targetDate` (derived MISSED) |
| Optional same-Project links | Issue, Phase, Deliverable, WorkPackage — no cascade |
| Cross-tenant negative | Org B ids must not appear in Org A planner |

Emails stay `@amber.test`. Idempotent slugs. Resettable via existing Local RC `rehearse-reset.sh` (drop → migrate → seed). Cloud/shared staging seed is **not** authorized (**LOCAL ONLY**).

Catalog seed (`prisma/seed.ts`) already upserts `task.*` / `milestone.*` permission definitions and role-template copies. No new codes.

## Rollback

Operational rollback = **restore backup / do not apply** the next forward migration. Amber does not ship reverse migrations that drop history (same as [m3-migration-plan.md](../development/m3-migration-plan.md)).

If only indexes were added, rollback is restore-or-leave-indexes (they do not destroy rows). If a bad seed runs locally, `pnpm local-rc:reset` / `rehearse-reset.sh` rebuilds the disposable database.

Audit events remain insert-only; rollback must not `UPDATE`/`DELETE` `audit.audit_events`.

## Compatibility with live Local RC data

Homologated Local RC databases that already contain PF-1.5 Tasks (from integration tests or manual API use) must keep those rows. Forward migrations are expand-only. M4 UI may render pre-existing Tasks without a data wipe.

## HUMAN_REQUIRED

None for M4.1. If a later WI believes a CHECK or column must change, stop and escalate — do not silently migrate.
