# M5.1 migration, seed, and rollback plan

**Status:** Additive forward migration **is applied** as empty Calendar/Messaging tables. No historical rewrite.  
**Issue:** [#82](https://github.com/Bruno2K/monolito-amber/issues/82).  
**Base:** `main` @ `9159889de55b73bbe7cb4eb1e7700f7c4a57fcef`.

## KEEP (do not rewrite)

All existing versioned migrations under `prisma/migrations/` through M3.7. Operational tables in `planning`, `operations`, `coordination`, `governance`, `project`, `document`, `org`, `identity`, `audit`, `jobs` are not dropped, truncated, or re-CHECKed.

Historical `planning.tasks.responsible_discipline_id` stays a string.

## Forward (this WI)

Migration `20261002070000_m5_1_calendar_messaging_baseline`:

1. `CREATE SCHEMA IF NOT EXISTS calendar` / `messaging`.
2. Tables: `calendars`, `calendar_access_grants`, `calendar_events`, `conversations`, `messages`, `message_read_states`.
3. CHECKs for status/kind/XOR/time-shape/Direct pair order.
4. Partial unique indexes for active USER/TEAM grants and DIRECT pairs.
5. Same-tenant triggers.
6. `GRANT` to `amber_app` (SELECT/INSERT/UPDATE/DELETE). Audit schema privileges unchanged (still no UPDATE/DELETE).

Referenced source ids are **not** foreign keys (no cascade into Planning/Operations/Governance).

Permission catalog: seed upserts `calendar.admin` and `message.moderate` from `PERMISSIONS`. Role templates are not granted those codes. Existing org-owned RoleDefinitions are not silently expanded.

## Seed / fixtures

`packages/shared/src/m5-seed-design.ts` is the plan. `M5_SEED_APPLIED_IN_M51 = false`. M5.2/M5.4 write rows using existing M3 users (`coord-a`, `contributor-a`, `suspended-a`, `team-a-structure`) and M4 Task `task-a1-todo`.

Catalog seed (`prisma/seed.ts`) already upserts every `PERMISSIONS` code — no separate permission SQL.

Emails stay `@amber.test`. Resettable via `rehearse-reset.sh`. Cloud/shared staging seed is **not** authorized.

## Rollback

Operational rollback = **restore backup / do not apply** the next forward migration. Amber does not ship reverse migrations that drop history.

If only this WI’s empty schemas exist, local reset (`pnpm local-rc:reset`) rebuilds the disposable database.

Audit events remain insert-only; rollback must not `UPDATE`/`DELETE` `audit.audit_events`.

## Forbidden in this or later M5 migrations

- `DROP TABLE` / `TRUNCATE` of Planning, Operations, or Identity history
- FKs from CalendarEvent to Task/Milestone/Deliverable/Gate that cascade-delete
- ResourceAllocation / TimeEntry / attachment / moderation tables
- `gate.override`
- Rewriting audit rows
- Enabling cloud deploy
